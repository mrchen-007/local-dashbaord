# 工程资料治理与风险稽查工作台调整技术 PRD

- 版本：V2.0
- 状态：可进入实施
- 技术策略：基于现有代码渐进式重构，不推倒重写
- 首期场景：工程合同与结算资料稽查

## 1. 产品定位

本产品面向施工企业项目管理、成本合约和内部审计人员，提供本地化工程资料治理、结构化数据提取、人工复核和风险稽查能力。

产品必须完成以下闭环：

```text
创建项目
  -> 绑定本地资料目录
  -> 扫描并治理文件
  -> 解析并提取字段
  -> 人工确认业务事实
  -> 生成项目正式台账
  -> 执行风险规则
  -> 查看来源证据
  -> 导出风险清单与审计报告
```

## 2. 调整原则

1. 保留 React、TypeScript、Tauri、Rust、SQLite、Python 服务和现有测试体系。
2. 将并列式工具页面调整为以项目为中心的业务流程。
3. 所有扫描、提取、复核、风险和报告数据必须关联 `project_id`。
4. AI 提取结果是观察值，不是正式业务事实；只有人工确认结果可以进入 ETL 和风险计算。
5. 每条风险必须能够追溯到来源文件、字段观察值、人工决策和规则版本。
6. 数据库通过增量 migration 演进，不得要求用户删除已有数据库。

## 4. 核心领域模型

### 4.1 Project

项目是系统的业务根实体，至少包含：

| 字段 | 说明 |
| --- | --- |
| `id` | 项目主键 |
| `code` | 项目编号，可为空但建议唯一 |
| `name` | 项目名称 |
| `source_root` | 本地资料根目录 |
| `owner` | 项目负责人 |
| `status` | 项目处理状态 |
| `created_at` | 创建时间 |
| `updated_at` | 更新时间 |

状态流转：

```text
draft -> scanning -> extracting -> reviewing -> ready -> archived
```

失败不会覆盖业务状态，批处理失败信息记录在 `processing_runs`。

### 4.2 ProjectFile

建议新增或完善 `project_files`，字段至少包括：

- `project_id`、`absolute_path`、`relative_path`
- `file_name`、`extension`、`file_size`
- `modified_time`、`content_hash`
- `scan_status`、`parse_status`、`error_message`
- `created_at`、`updated_at`

唯一约束：`project_id + relative_path`。

### 4.3 FieldObservation 与 FieldDecision

观察值保存模型输出和证据，决策保存人工处理结果。观察值不得因复核而被覆盖。

只有满足以下条件的数据可以进入项目正式台账：

```text
field_observations.review_status = confirmed
```

### 4.4 RiskFinding

建议新增 `risk_findings`：

- 项目、规则编码、规则版本、风险等级
- 标题、说明、状态
- 输入数据快照、证据引用
- 首次发现时间、最后计算时间

风险状态：`open`、`acknowledged`、`resolved`、`ignored`。

新增 `risk_actions` 保存处理人、处理动作、备注和时间，禁止覆盖历史处理记录。

### 4.5 FileOperation 与 ReportExport

`file_operations` 记录移动、备份、恢复和跳过操作；`report_exports` 记录报告类型、输出路径、规则版本和导出时间。

## 5. 分层技术架构

```text
React Page
  -> Domain Service
  -> src/api Tauri Adapter
  -> Rust Command
  -> SQLite / Local Files

React Page
  -> Extraction Service
  -> Python Local API
  -> Field Observation
```

边界要求：

1. 页面组件不得包含 SQL、路径安全逻辑或底层命令拼装。
2. 新 Tauri 调用统一进入 `src/api`，逐步迁移页面中的直接 `invoke`。
3. Rust 负责路径规范化、越界检查、文件操作和 SQLite 命令。
4. Python 只负责解析和推理，不直接写正式项目台账或风险结果。
5. Zustand 只管理当前项目、筛选条件和短期 UI 状态；SQLite 是业务状态真实来源。

## 6. 首期功能范围

### 6.1 项目中心

- 创建、编辑、归档和重新打开项目。
- 绑定本地资料目录，并验证目录存在且可访问。
- 显示文件数、失败数、待复核数、风险数和最后处理时间。
- 首次使用必须进入创建项目流程，不展示空白看板。

### 6.2 资料治理

- 不跟随符号链接，剪枝 `.git`、`node_modules`、`target`、缓存和备份目录。
- 支持 SHA-256 完全重复识别、文件名相似度和版本标签识别。
- 文件操作默认不覆盖、不直接删除；必须先备份并生成操作清单。
- 扫描任务支持进度、取消、失败重试和中断恢复。

### 6.3 数据提取与复核

首期字段：合同编号、合同金额、甲方、乙方、签订日期、结算金额、结算日期、质保比例。

复核动作：确认、修改确认、驳回、标记冲突。所有动作追加写入审计记录。

### 6.4 风险稽查

首期规则：

| 规则 | 条件 |
| --- | --- |
| 结算超合同 | 结算金额大于合同金额 |
| 关键金额缺失 | 已识别相关文件但金额未确认 |
| 合同编号冲突 | 同一项目存在多个已确认合同编号 |
| 重复结算资料 | 结算文件完全重复或高度相似 |
| 低利润风险 | 实际利润率低于配置阈值 |
| 证据不足 | 风险字段无法定位来源证据 |

### 6.5 报告中心

- 导出项目台账、风险清单和证据目录 Excel。
- 导出 Word 风险稽查报告。
- 报告内容必须注明生成时间、数据版本、规则版本和未确认字段数量。

## 7. 非功能要求

- 1 万文件扫描时界面保持可操作。
- 批处理记录总数、成功数、失败数、跳过数和耗时。
- 文件操作必须可回滚，恢复默认不覆盖目标文件。
- 数据库启用完整性检查和外键检查。
- 日志不得写入完整文档正文、密钥或敏感个人信息。
- Windows 安装包必须验证首次安装、升级迁移、卸载和数据保留。

## 8. 实施阶段

| Sprint | 交付内容 | 完成标准 |
| --- | --- | --- |
| 0 | 基线、结构审计、迁移策略 | 现有测试和构建通过，明确兼容边界 |
| 1 | 项目模型、项目中心、当前项目上下文 | 可创建项目并重新打开 |
| 2 | 项目文件模型、扫描任务接入 | 文件完整关联项目且支持恢复 |
| 3 | 提取任务和人工复核接入项目 | 未确认字段无法进入台账 |
| 4 | 正式台账和风险结果持久化 | 风险可重算、可处理、可追溯 |
| 5 | 项目工作台、报告中心 | 完成项目内完整业务导航 |
| 6 | 真实样本 E2E、安装与升级 | 新电脑可安装并完成真实闭环 |

## 9. 最终验收

使用一个脱敏真实工程项目目录，用户无需修改数据库或依赖模拟数据，即可完成创建项目、扫描资料、治理重复文件、识别版本、提取合同与结算字段、人工复核、生成风险、查看证据和导出报告。

项目达到可用状态的标准是业务闭环可稳定重复执行，而不是页面能够打开。
