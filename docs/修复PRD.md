# 工程项目智能数据中枢——技术修复 PRD

**文档版本**：v1.0  
**制定日期**：2026-07-13  
**文档状态**：待技术评审  
**关联文档**：`docs/整改PRD.md`  
**目标**：关闭阻塞真实使用的缺陷，并建立可重复验证的发布链路

## 1. 执行规则

### 1.1 优先级

- **P0**：阻止构建、可能丢失/误删数据、核心链路不可用或结果严重失真。
- **P1**：主要功能不完整、错误被隐藏、安全边界不足或无法维护。
- **P2**：性能、体验、工程质量问题，不阻塞内部试用但阻塞正式发布。

### 1.2 完成定义（DoD）

每个任务必须同时满足：

1. 代码实现完成并通过评审。
2. 对应自动测试通过。
3. 验收用例有实际运行记录。
4. 错误路径和回滚路径已验证。
5. 文档同步更新。
6. 不通过模拟数据或吞错方式绕过验收。

## 3. P0 修复任务

### FIX-001 统一 Tauri 与 SQL 插件技术栈

**现状**：前端同时存在 Tauri v1 API 与 SQL 插件 v2，Rust 后端为 Tauri v1，并从不可稳定获取的 Git 分支加载 SQL 插件，干净环境 `cargo check` 失败。

**涉及模块**：

- `package.json`
- `package-lock.json`
- `src-tauri/Cargo.toml`
- `src-tauri/Cargo.lock`
- `src-tauri/tauri.conf.json`
- `src/api/tauriApi.ts`
- `src/shared/database.ts`

**实施方案**：

1. 建立独立迁移分支，选择并锁定单一 Tauri 主版本。
2. 推荐方案：统一到 Tauri v2 官方 SQL 插件；若选择 v1，前端插件也必须降到兼容版本且禁止 Git 浮动依赖。
3. 所有 Rust/Node 依赖使用固定兼容范围并提交锁文件。
4. 更新配置格式、权限声明、invoke 导入路径和插件初始化方式。
5. 在无缓存环境执行安装、前端构建、`cargo check` 和桌面打包。

**验收用例**：

- 删除依赖缓存后能够按锁文件恢复依赖。
- `npm run build`、`cargo check --locked`、桌面开发启动和安装包构建均通过。
- 仓库中不存在 `tauri-plugin-sql` Git URL 或 v1/v2 混搭。

### FIX-002 统一 Tauri 命令契约

**现状**：前端与 Rust 的参数名、返回值存在多处不一致，例如清单使用 `path`/`folder_path`，解析使用 `path`/`file_path`，恢复接口的数据结构不一致。

**实施方案**：

1. 为每个命令建立明确的 request/response：
   - `scan_directory`
   - `get_manifest`
   - `parse_file`
   - `extract_fields`
   - `move_to_backup`
   - `restore_from_backup`
   - `update_file_manifest`
2. Rust 使用结构体接收复杂请求并派生序列化类型。
3. 前端统一从 `src/api/tauriApi.ts` 调用，页面不得直接 `invoke`。
4. 返回统一信封：`{ success, data, error, warnings }`，或采用 Tauri `Result<T, AppError>`，全项目只能选择一种。
5. 为错误定义稳定错误码，如 `PATH_NOT_FOUND`、`PERMISSION_DENIED`、`SERVICE_UNAVAILABLE`。

**验收用例**：

- 每个命令至少包含成功、参数错误、资源不存在三个契约测试。
- TypeScript 类型与 Rust JSON 快照一致。
- `rg "invoke<|invoke\(" src` 结果只允许出现在 API 封装层。

### FIX-003 修复解析/抽取服务链路

**现状**：Python `/extract` 返回 `success/results/error/duration_ms`，前端期望 `file_path/fields/confidence/duration_ms`；健康接口只判断 `status=ok`，即使模型未加载也可能被判定可用。

**实施方案**：

1. 定义统一响应：

```json
{
  "file_path": "...",
  "fields": {},
  "field_confidences": {},
  "model": "...",
  "duration_ms": 123,
  "warnings": []
}
```

2. Rust 对 HTTP 非 2xx、`success=false`、响应超时和 JSON 不合法分别映射错误。
3. HTTP 客户端增加连接和整体超时，避免 UI 永久等待。
4. 健康检查要求 `status=ok && model_loaded=true`。
5. `parse_file.py` 路径不得依赖进程当前目录；开发态使用资源路径，发布态使用 sidecar/resource 路径。
6. 页面开始任务前执行服务预检，并提供“重试/跳过 AI/打开诊断”入口。

**验收用例**：

- 模型正常、模型未加载、端口未启动、超时、错误 JSON 五种场景均返回正确 UI 状态。
- 使用 1 份 PDF、1 份 DOCX、1 份 XLSX 完成解析和字段入库。
- 服务不可用时不显示“处理完成”。

### FIX-004 重构数据库迁移和写入

**现状**：Schema 同时存在于 SQL 和 TypeScript；`INSERT OR REPLACE` 可能改变主键并破坏关联；未明确启用外键；缺少迁移版本和事务。

**实施方案**：

1. `migrations/` 作为唯一 Schema 来源，采用正式迁移执行机制。
2. 新增 `schema_migrations` 或使用插件内置 migration 版本管理。
3. 启动连接执行：`PRAGMA foreign_keys=ON`、合理的 `journal_mode=WAL` 和 `busy_timeout`。
4. 将 `INSERT OR REPLACE` 改为 `INSERT ... ON CONFLICT(...) DO UPDATE`，保留原主键。
5. 为 `parsed_contents.file_id`、`extracted_fields.file_id` 建立唯一约束后再 UPSERT。
6. `upsertFile` 不依赖不同驱动不一致的 `RETURNING/lastInsertId` 组合；UPSERT 后按唯一路径查询 ID。
7. 批量写入使用事务，失败时整批回滚或明确采用逐项结果模式。
8. 为迁移前数据库创建时间戳备份。

**验收用例**：

- 同一路径更新 10 次后 `files.id` 不变，关联数据仍存在。
- 中途注入 SQL 失败后事务结果符合设计，不产生半套数据。
- 从空库和上一版本数据库升级均成功。
- `PRAGMA integrity_check` 返回 `ok`，`PRAGMA foreign_key_check` 无记录。

### FIX-005 重构备份与恢复协议

**现状**：备份文件名仅添加秒级时间戳，不保留原目录；同名文件有覆盖风险；恢复统一放入一个目录并可能覆盖已有文件。

**目标目录结构**：

```text
.dedup-backups/<operation-id>/
  operation.json
  files/<原相对目录结构>
```

**操作清单最小字段**：操作 ID、创建时间、工作区根路径、源相对路径、备份相对路径、大小、哈希、状态、错误。

**实施方案**：

1. 前端先提交 Dry-Run 计划，后端重新验证所有源文件仍未变化。
2. 源路径必须位于当前授权工作区内，备份路径必须位于应用备份根目录内。
3. 先复制到临时文件，校验大小和哈希，原子重命名成功后再删除源文件。
4. 每文件返回成功/失败/跳过，操作状态支持 `partial`。
5. 恢复按清单原路径执行，默认冲突策略为 `skip`，可选 `rename`，覆盖需二次确认。
6. 中断后依据清单恢复操作状态，不重复删除或覆盖。

**验收用例**：

- 不同目录同名文件可同时备份并原位恢复。
- 文件名含下划线、中文、超长路径时恢复正确。
- 目标已存在、磁盘空间不足、文件被占用、任务中断时无原文件丢失。
- 随机抽取与全量恢复后的哈希均与操作前一致。

### FIX-006 移除生产 mock 回退

**现状**：数据库为空、非 Tauri 环境或读取失败时，看板自动展示模拟项目；版本页面直接使用模拟文件。

**实施方案**：

1. 删除生产数据仓库中的 `generateMockProjects()` 回退。
2. 空库、环境不支持、数据库错误分别显示不同状态。
3. 如需演示，增加独立 `DEMO_MODE` 构建标志和明显水印，演示库与生产库物理隔离。
4. 版本比对必须选择真实目录并使用扫描结果。
5. 导出功能禁止导出演示数据，或必须带“演示数据”水印。

**验收用例**：

- 空库时项目数为 0 且显示导入指引。
- 断开数据库时显示错误，页面不得出现任何预置项目名。
- 生产构建包内不包含 mock 数据模块，或不可从正常入口触发。

### FIX-007 修复批处理状态和错误统计

**现状**：解析/抽取失败结果被过滤，保存失败只记录控制台，最后仍设置为完成并显示“所有文件已保存”。

**实施方案**：

1. `processInParallel` 返回结构化 `TaskResult<T>`，不得以 `undefined` 表示失败。
2. 每阶段维护总数、成功、失败、跳过、取消和待重试数量。
3. 文件状态随阶段更新，失败写入 `error_code/error_message`。
4. 最终状态根据结果计算：全成功为 `succeeded`，部分失败为 `partial`，全失败为 `failed`。
5. 页面提供失败列表、错误筛选和批量重试。
6. 任务级异常必须通过 `try/catch/finally` 释放运行状态。

**验收用例**：

- 10 个文件中注入 2 个解析失败、1 个保存失败，最终显示 7/2/1 明细并标为部分完成。
- 重试只处理失败文件，不重复处理已成功项。
- 用户取消后显示取消数量，不显示成功完成。

## 4. P1 修复任务

### FIX-008 修复扫描剪枝、链接和变化检测

1. 使用 `WalkDir::filter_entry` 真正阻止进入忽略目录。
2. 默认 `follow_links(false)`，可选开启并进行循环/越界检查。
3. 忽略规则支持默认值和用户配置，并在结果中统计忽略数量。
4. 哈希前后检查大小和修改时间，变化则标记 `FILE_CHANGED`。
5. 扫描后端支持取消令牌和节流进度事件。

**验收**：带大型 `node_modules` 的样本中不出现任何子文件；目录联接不会越过工作区；取消响应满足产品 PRD。

### FIX-009 版本比对接入真实数据

1. 增加真实目录选择或复用当前工作区扫描结果。
2. 将“完全重复”和“版本候选”分开展示。
3. 版本规则覆盖 `v1/v2`、日期、最终版、修订版等，并输出依据。
4. 不能仅凭修改时间自动清理旧版；版本页只生成候选计划。
5. 修复渲染中对状态数组原地 `.sort()` 的副作用，统一使用副本。

**验收**：黄金样本版本组准确率达到评审约定，页面不出现“正在加载模拟数据”。

### FIX-010 增加字段复核和来源追溯

**数据库新增建议**：

- `field_observations`：每个来源文件的原始抽取值、标准值、置信度和片段。
- `field_decisions`：用户确认/修改/驳回记录。
- `processing_runs`：处理批次和模型/规则版本。

**实施要点**：

- 不同来源记录不得互相覆盖。
- 低置信度、格式错误和多来源冲突自动进入复核。
- 看板字段可打开来源抽屉，定位到文件和文本片段。
- 用户修改后记录前值、后值、时间，不修改原始观察值。

**验收**：任一正式看板金额均能追溯到确认记录或确定性数据来源。

### FIX-011 修复 ETL 与热更新语义

1. ETL 使用处理批次或 `updated_at > last_successful_sync` 作为增量边界。
2. 同一批 ETL 在事务中执行，成功后才更新同步游标。
3. 空值保持空值，禁止用 0 掩盖缺失数据。
4. 热更新比较最新时间与上次游标，而不是“数据库存在记录即有更新”。
5. 防止轮询重叠执行；应用后台或任务运行中采用退避策略。
6. 聚合幂等：同一输入重复运行结果不增加重复子表记录。

**验收**：无新数据时连续轮询不触发刷新；同一批次重复 ETL 后行数和指标不变。

### FIX-012 收紧桌面权限与 CSP

1. 移除全盘 `fs-all` 和 `scope:["**"]`，改为用户授权目录与应用数据目录。
2. 启用最小 CSP，只允许本地资源和明确的 `127.0.0.1` 服务连接。
3. Sidecar 参数使用白名单，不允许任意参数。
4. 所有文件操作在 Rust 端执行路径规范化和工作区边界校验。
5. 记录安全评审清单，不在日志打印文档正文。

**验收**：对工作区外路径调用敏感命令返回拒绝；应用核心页面在 CSP 下正常工作。

### FIX-013 改造运行时和启动器

1. 不依赖用户全局 Python、pip、Node 或 Rust运行正式安装包。
2. Python 服务使用内置 sidecar/受控环境，版本随应用发布。
3. 启动器设置最大等待时间，模型未就绪时给出失败原因和重试选项。
4. 健康检查区分“进程在线”和“模型可用”。
5. 应用退出时只终止自己启动的服务实例，不按窗口标题批量杀进程。
6. 首次模型安装/下载需要进度、校验、取消和离线包方案。

**验收**：没有开发工具的干净 Windows 虚拟机可以安装并使用全部已购买/安装组件。

## 5. 测试与发布任务

### FIX-014 自动测试与 CI 门禁

**测试层级**：

| 层级 | 最低覆盖 |
|---|---|
| TypeScript 单元测试 | 去重规则、版本规则、字段映射、风险规则、格式转换 |
| Rust 单元测试 | 路径边界、扫描忽略、备份清单、冲突策略 |
| 数据库集成测试 | 空库迁移、旧库升级、UPSERT、事务回滚、外键完整性 |
| Python 测试 | 健康状态、请求校验、抽取响应结构、模型不可用 |
| 端到端测试 | 扫描→解析→抽取→复核→ETL→看板→导出→恢复 |

**CI 门禁**：

- 格式检查、TypeScript 类型检查和 lint。
- 前端生产构建。
- Rust format、clippy、test、check。
- Python lint/type/test。
- 数据库迁移测试。
- 生成安装包前执行黄金样本冒烟测试。

**质量目标**：核心纯逻辑模块语句覆盖率不低于 80%；整体覆盖率不作为唯一目标，但所有 P0/P1 修复必须有回归测试。

### FIX-015 发布、诊断和文档

1. 建立语义版本和变更日志。
2. 生成 Windows 安装包，验证安装、升级、降级阻止和卸载。
3. 数据库升级前自动备份，升级失败自动恢复。
4. 增加“关于/诊断”页面：应用版本、数据库版本、服务状态、日志目录、诊断包。
5. 重写快速开始和操作手册，删除未经验证的性能和完成度描述。
6. 删除外层重复 Node 包或明确仓库根目录，避免用户在错误目录安装依赖。

## 8. 端到端验收脚本

正式发布前必须人工执行并留存记录：

1. 在干净 Windows 测试机安装应用。
2. 创建新工作区，选择黄金样本目录。
3. 确认预扫描总数、忽略数和失败数符合真值。
4. 执行扫描并中途取消一次，确认可安全重新开始。
5. 检查完全重复组和版本候选组。
6. Dry-Run 后备份选定重复文件，检查源目录和操作清单。
7. 恢复全部文件，比较目录树和哈希与操作前一致。
8. 解析支持格式，验证成功、失败、跳过明细。
9. 在 AI 服务不可用场景执行一次，确认可见错误和降级模式。
10. 正常抽取后复核冲突字段，执行 ETL。
11. 检查看板、风险下钻、来源追溯和报告导出。
12. 重启应用，确认数据和任务历史仍存在。
13. 升级到下一测试版本，确认数据库迁移和备份正常。

## 10. 发布否决条件

满足任一条件必须停止发布：

- 桌面安装包无法在干净环境构建或启动。
- 存在可能误删、覆盖或无法恢复用户文件的已知缺陷。
- 生产流程仍会混入模拟数据。
- 部分失败仍被显示为全部成功。
- 数据库迁移无法回滚或完整性检查失败。
- 核心字段或风险结果无法追溯来源。
- 存在未关闭 P0/P1 缺陷。
